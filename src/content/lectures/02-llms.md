## 本讲要解决什么问题

CS329Z 主要工作在“LLM 应用与智能体”这一层，但模型的生成方式、上下文长度和推理成本会直接影响系统设计。第二讲沿着**语言模型是什么 → 架构 → 训练 → 推理 → 智能体应用**五条线，建立开发者需要的模型直觉。原 PDF 含大量逐步展开的动画页，下文按知识主题整理。

## 一、语言模型如何生成文本

自回归语言模型把一个 token 序列的概率分解为逐步预测的乘积：

$$
P(x_1,\ldots,x_n)=\prod_{t=1}^{n}P(x_t\mid x_1,\ldots,x_{t-1}).
$$

例如生成 “The class was about agents.”，模型先估计 `The` 的概率，再估计已知 `The` 时 `class` 的概率，依此类推。实际计算常把概率取对数后求和，避免多个小数相乘导致数值不稳定。模型学习的是数据分布，因此可以从下一 token 的概率分布中**采样**，而不是只能给出一个固定分类结果。

采样策略决定输出风格和成本。贪心解码总选概率最高的 token；top-k 只保留最高的 k 个候选；top-p 保留累计概率达到阈值的候选；温度调整分布的尖锐程度；束搜索同时保留若干候选路径。代码与数学任务通常更重视可预测性，创意写作可能需要更高的多样性。选策略时还要考虑计算预算。

## 二、架构为什么影响智能体

从 n-gram、循环神经网络到 Transformer，语言模型不断改变处理序列的方式。本讲重点是**仅解码器 Transformer**：输入 token 先映射为向量并加入位置信息，再通过多层因果注意力，只读取当前位置及之前的内容，最后输出下一个 token 的概率。多头注意力让模型从多个表示空间寻找关联。

普通全局注意力可以让每个 token 查阅所有之前的 token，但处理长度为 $n$ 的序列时，注意力计算通常随 $n^2$ 增长；长上下文因此昂贵。线性注意力用压缩状态表示过去的信息，理论上的长度开销更接近 $O(n)$，状态内存可保持常量，但细粒度长距离信息可能更难保留。讲义也提到混用全局注意力与线性注意力的架构。

**上下文长度并不只是“模型能接收多少字”的配置。** 位置表示、训练时见过的长度、推理内存以及模型能否真正利用远处信息，都影响效果。智能体会累积工具结果、文件和历史行动，了解这些限制有助于选择模型、控制上下文，并设计外围运行框架。

## 三、训练阶段塑造了什么能力

训练的基本目标是让真实下一个 token 的预测概率更高。若正确 token 的概率为 $p$，其负对数损失为 $-\log p$；在整个词表上写出来，就是交叉熵损失。讲义用 “The class was about how …” 说明：当真实下一个 token 是 `how` 时，模型应提高它的概率。

训练数据与训练阶段有不同作用：

| 阶段 | 主要做法 | 对智能体的影响 |
| --- | --- | --- |
| 预训练 | 从大量文本等数据中学习通用分布；数据要抽取、过滤、去重和混合 | 获得基础知识与语言能力 |
| 中期训练 | 调整数据混合，增加数学、代码等目标领域 | 加强特定领域的表现 |
| 后训练 | 指令微调、从人类偏好学习，或用可验证奖励进行强化学习 | 改善遵循指令与解题行为 |
| 智能体专项训练 | 利用软件工程等任务轨迹训练 | 适应工具调用与多步任务 |

人类偏好并非完美信号：标注者之间存在差异，反馈也可能诱导迎合或过度自信。可验证奖励则用单元测试、精确答案、形式化证明或环境状态提供明确反馈，尤其适用于数学和代码；但奖励检查器本身的设计仍可能出问题。

## 四、推理成本来自哪里

一次生成可分为 **prefill** 和 **decode**。Prefill 处理输入提示词，能较好地并行；decode 逐 token 生成，通常受到读取模型权重与 KV 缓存的开销约束。随着智能体反复调用模型，输入长度、输出长度、延迟和吞吐量都会直接影响产品体验与成本。推测解码让较小模型先草拟 token，再由目标模型验证，是一种加速方法。

推理阶段也可以花更多计算换答案质量：例如生成思维链、提高推理预算，或多次采样后由验证器选答案。没有外部验证器时，可以比较多条推理链的最终答案，使用**自洽性**。讲义的夹克例子很适合检查“看似会推理”的答案：80 美元先涨价 25%，再按新价格打 75 折，结果是 $80\times1.25\times0.75=75$ 美元；两个百分比不能直接抵消，因为基数不同。

## 五、把模型接入智能体

智能体中的多个组件需要共享明确的输入输出契约。**结构化 I/O** 用固定字段表达决策与工具参数；约束解码可限制输出格式，减少无效调用。工具调用不是一句自然语言愿望，而是要产生符合接口结构的名称和参数，再交给系统验证执行。

另一项关键工作是**上下文工程**：决定系统提示、消息历史、记忆、工具返回结果和附件中的哪些信息进入模型。不能简单地“全放进去”。上下文膨胀会带来成本，也可能使模型忽略相关信息；工具太多还会加重选择负担。讲义建议通过检索找回相关记忆，尽量顺序追加内容以利用 KV 缓存，并用基准任务实测上下文调整的效果。

当历史太长时可以**压缩上下文**，但要决定保留哪些目标、约束和已完成工作。保留过多会很快再次超长；删掉关键状态则可能使智能体重复劳动或改变目标。上下文设计因此是可测量的系统问题，而不是越长越好。
