## 写出代理只是工程循环的起点

一个能回答问题的演示程序，离稳定服务还有一段距离。讲义把 AI 系统工程拆成三个支柱：**数据**提供训练样本、示范和运行轨迹；**系统或模型**决定如何组合语言模型、工具与程序逻辑；**评估**给出通过率、准确性、成本和延迟等反馈。工程循环是「构建 → 运行 → 评估 → 改进」。框架能省去重复工作，但也会隐藏细节，所以需要知道它替我们做了什么。

先看控制流：只调用一次模型时，程序的大部分工作由模型完成；在**工作流**中，代码编排多个模型调用和工具；在**代理**中，模型根据观察决定下一步。选择框架之前，应明确任务需要多大的自主决策空间。固定的分类、检索、起草流程未必需要一个自由探索的代理。

## DSPy：把模型调用写成可优化的程序

DSPy 用三个概念组织语言模型程序：

| 抽象 | 回答的问题 | 作用 |
| --- | --- | --- |
| Signature | 要输入和输出什么？ | 规定模型调用的输入、输出契约 |
| Module | 怎样完成任务？ | 组合签名与程序逻辑，形成可调用组件 |
| Optimizer | 如何提高指标？ | 利用数据和评测指标改进提示或权重 |

例如，先定义「输入：用户问题与相关文档；输出：有依据的答案」的契约，再选择直接预测、思维链或多候选等实现方式。讲义列出的模块有 `dspy.Predict`、`dspy.ChainOfThought`、`dspy.BestOfN`，也有面向代理的 `dspy.ReAct`、`dspy.RLM`。一个模块不是质量保证；若希望优化器改进它，必须提供与实际任务接近的数据，并定义可以比较好坏的指标。只优化通用问答分数，未必会改善本课程项目中的真实业务任务。

这种写法的价值在于把**任务契约**与**实现策略**分开。你可以改变模块内部的调用方法，仍用同一组样本评估输出是否符合契约。讲义强调 DSPy 把数据、指标、程序改进放到同一个工作流程中。

## LangGraph：让控制流和状态可见

LangGraph 把工作流表示为图。**State** 是节点共享的工作区，可以包含消息历史或其他任务状态；**Node** 读取状态并产生更新；**Edge** 指定下一步，条件边则根据结果选择分支。一个简化的工具代理可以画成：

`START → LLM →（需要工具？）→ Tools → LLM → END`

如果模型判断无需工具，就直接走向结束；如果需要工具，执行结果写回状态，模型再决定是否继续。这里最重要的设计问题是：哪些分支应由代码决定，哪些决定交给模型？把所有逻辑都写成固定边容易失去适应性；全部交给模型又会使运行路径难以预测。图和共享状态使这些选择能够被明确讨论、追踪和测试。

DSPy 和 LangGraph 关注的抽象层不同。前者突出签名、模块和基于指标的优化；后者突出状态、节点和边。二者都可以组合模型调用与工具，不能仅凭框架名字推断系统是否「有代理性」。

## Agent harness：模型外面还要设计什么

**Agent harness** 是让模型持续观察、调用工具、维护上下文并执行任务的外层系统。讲义用几个开源项目展示了不同选择：

- **mini-SWE-agent** 只给模型 `bash`，消息历史按线性顺序追加，每次动作作为独立子进程执行。
- **OpenHands** 把动作保存为事件，再由事件重建发给模型的消息；持久终端让目录和环境状态跨命令保留，还会检测重复动作以避免卡住。
- **Pi** 默认只有 `read`、`write`、`edit`、`bash` 四个工具，历史可以从旧节点分叉，整体保持极简。
- **OpenClaw** 展示了常驻网关与定时「心跳」等长期运行方式。

这些差异会影响调试能力、成本、延迟和用户控制。线性历史容易理解，事件日志便于重建与审计；持久终端适合连续操作，也需要管理环境状态；工具少降低选择负担，但可能限制任务能力。判断一个 harness 是否适用，应比较它支持的任务和运行约束，而不是只看提供了多少功能。

## 编排与遥测：让长任务可以恢复

代理可能连续运行很久，外部 API 会超时，工具也会偶发失败。**Temporal** 用持久化工作流处理这类问题。讲义的执行模型中，**Activity** 是可能失败的工作单元，**Workflow** 连接活动，worker 从队列接取任务，服务器保存执行历史与状态。课程演示了活动重试和由服务器管理的计时：进程中断以后，任务进度和下一步仍有据可查。

可靠性与可观测性是两件相连的事。重试使任务有机会恢复；**追踪**告诉我们它为何失败、重试了几次、调用了什么模型和工具、状态怎样变化。讲义还列出 MLflow、LangSmith、Langfuse 等观测工具。工具名字可以变化，实际要记录的内容比较稳定：模型输入输出、工具参数与结果、状态更新、错误、时间与费用。

给一个自动生成报告的系统设计失败处理时，可以逐项问：检索超时是否重试？重试上限是多少？报告生成失败后能否从已完成的检索继续？用户能否看到任务状态？没有这些答案，演示顺利运行一次并不代表系统可运营。

## 工程原则与复习

讲义最后要求从简单方案出发，必要时再增加框架和自主性；为失败设置超时、重试上限与执行预算；用代表性的任务、边界情况和失败场景评估质量、成本与延迟。框架增加抽象，也增加依赖。出现问题时，应沿追踪记录回到具体模型调用、工具调用和状态变化，而不是只在框架外层调整提示词。

复习这讲时，试着回答三个问题：你要优化的是输出质量还是运行可靠性？任务控制流位于代码还是模型？失败后，能否从日志和持久状态准确复原发生了什么？
