## 从一个算术问题开始

用户问「17,423 × 892 等于多少？」语言模型可以直接猜一个数字，也可以调用计算器，再把结果写成回答。后者看似多了一步，却把「生成文字」和「执行精确计算」交给了各自擅长的系统。课程把**工具**定义为在模型外部运行的函数接口：模型决定是否调用、选择函数并生成参数，外部程序执行后把结果送回模型。工具可以是计算器，也可以是搜索、数据库、浏览器或业务 API。

本讲承接检索增强生成（RAG）。检索器即使找到更多文档，阅读器也未必能有效利用它们：证据可能漏检，相关内容可能落在长上下文中不易注意的位置，早期的错误又会在后续循环中放大。讲义中的实验说明，检索召回率继续增长时，RAG 效果可能在加入约 10–20 篇文档后就趋于饱和。RAG 的引用也由模型生成，因此引用本身仍须核验。工具调用把问题从「给模型更多文字」扩展为「让模型在合适的时刻取得可执行、可验证的结果」。

## 为什么智能体需要工具

可以从三类能力缺口判断是否该接入工具。

| 能力缺口 | 可用工具 | 典型任务 |
| --- | --- | --- |
| 模型难以稳定完成的精确操作 | 计算器、代码解释器、符号求解器 | 大数运算、逻辑验证、确定性转换 |
| 训练时未见或不能公开训练的知识 | 搜索、实时 API、私有语料检索 | 最新事件、冷门事实、内部文档 |
| 模型无法直接触及的状态和环境 | 数据库、浏览器、传感器、机器人 | 查询订单、操作网页、读取当前价格 |

这并不意味着每个请求都要调用工具。比如一句普通的改写请求，直接回答通常更简单。智能体应先判断外部执行是否能带来所需的准确性、新鲜度或操作能力，再承担额外的延迟、费用和失败风险。

## 模型怎样学会调用工具

**Toolformer** 展示了自监督学习的一种路线。研究者先为少量 API 准备调用示例，再让模型在文本的候选位置提出调用，实际执行这些候选调用，并比较「有调用结果」与「没有调用结果」时预测后续词的损失。只有帮助预测的调用才保留，最后用扩充的数据微调模型。讲义以「Pittsburgh is known as the Steel City」为例：模型可以在句子中插入问答 API 调用，请外部系统提供匹兹堡的别称；如果回答确实改善后续预测，这次调用便可能成为训练样本。关键不是记住这个城市，而是学习**何时调用、传什么参数、怎样使用返回值**。

**ToolkenGPT** 采取另一种表示方式：把每个工具编码成一个特殊 token，模型像预测下一个词一样预测是否使用该工具，然后生成参数。训练时会跳过由工具返回、并非模型自己预测的结果 token。两者都在教模型使用工具，但调用在模型内部的表示不同：Toolformer 把调用写进文本，ToolkenGPT 学习工具 token 的向量。

工具数量增长后，选择本身变成难题。**ToolLLM** 配合 API 检索器，从一万六千多个 API 中推荐候选，再让模型完成调用。**Gorilla** 使用约 1,645 条 API 调用数据训练，并在训练中加入正确和错误的检索内容，让模型学习何时信任检索结果。讲义用抽象语法树（AST）子树匹配衡量生成的 API 调用，关注「看起来合理、实际却不存在或参数不对」的幻觉。几种方法分别从训练样本、调用表示、检索候选和结构化校验解决不同环节的问题。

## 从 HTTP 到可发现的工具

模型学会调用之外，还需要知道工具叫什么、输入什么、结果怎样返回。讲义把接口演进概括为三个层次：

1. **REST API** 提供 HTTP 地址，例如 `GET /v1/weather?city=Stanford`。调用者需要事先掌握路径、参数和响应格式。
2. **Function calling** 用 JSON Schema 描述函数名、参数类型和必填字段。模型输出函数名与参数，宿主程序验证并执行，再把结果交还模型。
3. **MCP** 把工具发现和执行放进通用协议。宿主中的客户端通过 `tools/list` 向服务器查询可用工具及输入 schema，再通过 `tools/call` 带参数执行。

课程用教学管理系统说明第三层：原本的 `GET /assignments`、`POST /grade` 等 REST 路由可以暴露为 `list_assignments`、`post_grade` 等 MCP 工具。此时要分清两段权限：智能体访问 MCP 服务器的**入站身份验证**，以及 MCP 服务器访问教学管理系统的**出站凭据**。把接口标准化并不会自动解决权限问题；调用链上的每个边界都要明确谁有权做什么。

## 评估一次调用与完整任务

工具调用不能只看模型有没有输出合法 JSON。**BFCL** 考察函数选择、参数、多函数或并行调用，以及没有合适函数时是否能判断「不能调用」；它使用 AST、真实执行和多步状态等不同方式评估。讲义中的小例子给出 `add(a, b)` 和 `mult(a, b)`：问 `2+3` 应调用加法；问两道加法题可并行调用；如果只提供加法函数却要求乘法，正确行为是识别工具不适用。

**ToolBench** 把范围扩展到大量真实 API；**τ-bench** 则把用户交互、业务规则和多轮工具操作放进测试。一次成功还不够，讲义用 `pass^k` 强调重复运行的一致性：同一任务做多次，只偶尔成功的智能体不能称为可靠。常见失败包括选错工具、编造字段或单位、跳过前置步骤、重复一个已失败的调用，以及该询问用户时擅自行动。

## 复习与实践

- 给一个任务选工具时，先指出模型缺的是精确计算、外部知识，还是访问环境的能力。
- 区分「训练模型学会调用」与「运行时通过 schema 发现和执行工具」；两者可以结合。
- 设计评测时同时检查函数选择、参数、执行后的状态，以及多次运行的稳定性。
- 画出调用链中的权限边界，再决定哪些操作允许自动执行。
