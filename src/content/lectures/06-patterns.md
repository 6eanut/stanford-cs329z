## 先决定谁控制下一步

设想一个客服系统。若任务总是「识别工单类型 → 检索政策 → 起草回复」，代码可以把步骤固定下来；如果问题可能需要查询订单、检查日志、向用户追问，再决定下一步，模型就需要在运行中选择行动。前者是**工作流**，控制流主要在程序；后者是**代理**，控制流更多由模型根据观察决定。工作流较容易复现和调试，代理较能应对不确定路径。真实系统常把两者结合：外层固定审批或预算边界，内部让代理探索解决方案。

设计模式不是现成答案。讲义强调，模式只提供可复用的结构，必须根据环境、失败成本和评测结果调整。本讲从流程结构、推理与行动方式、上下文管理三层来拆解代理设计。

## 五种常见工作流模式

| 模式 | 做法 | 适合的问题 |
| --- | --- | --- |
| 提示链（Prompt Chaining） | 把大任务拆成顺序步骤 | 步骤明确，分步核验可提高准确率 |
| 路由（Routing） | 先分类，再送到不同提示或模型 | 请求类型差异大，简单请求可用较轻模型 |
| 并行（Parallelization） | 独立任务同时执行，或对同题多次采样后投票 | 各部分可并行、需要多种视角 |
| 编排器—工作者（Orchestrator-Workers） | 一个模型动态拆任务并分派工作者 | 子任务数量和内容难以预先写死 |
| 评估器—优化器（Evaluator-Optimizer） | 生成、反馈、修改形成循环 | 反馈标准清楚，生成器能依据反馈改进 |

提示链通常用更多调用和延迟换取分解后的可控性。并行有两种用法：**分区**让不同调用各处理一部分，例如同时进行安全分类与内容处理；**投票**让多个调用处理同一问题，最后汇总。编排器—工作者看起来也有多个并行分支，但分支由运行时的模型动态创建。评估器—优化器则需要真正有用的反馈；若评价标准模糊，反复生成未必能改进结果。

讲义用 **STORM** 展示多种模式的组合，包括提示链、并行、工作者和近似的评估优化步骤；**Archon** 展示对推理时组合架构进行搜索。实践中，一个较大的系统往往由几个基本模式拼成。描述它时，最好画出实际步骤与数据流，而不只给整个系统贴一个「多代理」标签。

## 推理和行动：代理怎样使用工具

给模型工具以后，还要确定它以什么节奏思考、调用和修正。

**ReAct** 把推理与行动交替安排：模型先根据当前信息决定行动，调用工具，观察结果，再决定下一步。这适合需要边查边做的任务。**Reflexion** 在多次尝试之间引入反思：代理依据外部环境反馈总结失败原因，把总结作为下一次尝试的记忆。讲义特别提醒，单纯要求同一个模型评价自己的回答可能降低表现；Reflexion 的关键是利用外部反馈，而不是把自我评价当成可靠的正确性证明。**CRITIC** 进一步让验证者使用外部工具核查结果。

**CodeAct** 关注行动的表达形式。相比连续生成许多狭窄的 JSON 动作，代理可以写一段代码来组织调用和计算。讲义的例子要比较美国、日本、德国、印度购买同一款手机的成本；代码可以把查询、汇率处理和比较串起来。原讲义报告代码行动在其测试任务中成功率更高、所需轮次更少；实际采用时仍需结合执行权限与任务评测。

还有一条路线是**先规划，再执行**。ReWOO 先写出要做的步骤，之后执行这些步骤，减少每一步都重新推理的开销；LLMCompiler 在此基础上加入可并行任务的执行与动态重规划。计划不是承诺执行环境永远不变：工具结果可能推翻假设，因此仍需要检查依赖、处理错误和调整后续步骤。

## 上下文管理：保留什么，移走什么

代理每轮都会积累消息、工具输出和中间结果。把全部历史原样塞回模型，既费 token，也会让重要约束淹没在旧日志里。讲义给出两个原则：**聚焦当前任务所需信息**，同时**保持连续性**，即保住目标、约束、已有决定和进度。实现上有五类模式：

1. **持久事件日志**：像 OpenHands 一样，按发生顺序保存动作和观察；每次调用模型时再从事件重建输入。完整记录与模型实际看到的上下文可以不同。
2. **记忆卸载**：把需要长期保存的知识写入记忆或文件，释放对话窗口；讲义以 MemGPT 为例。
3. **压缩**：把较早的推理、行动和观察总结成短描述，保留继续任务所需的信息。
4. **观察遮蔽**：把旧工具输出截断或隐藏。对代码代理尤其有用，因为一次构建或测试输出可能很长。
5. **上下文隔离**：让子任务只看到自己的材料，完成后返回结果；工具说明和技能文件也可按需逐步披露。

这些模式可以组合：系统保留完整事件日志供追溯，构建模型输入时遮蔽长输出，再把关键结论压缩或卸载到记忆。压缩若漏掉用户约束，会破坏连续性；事件日志虽完整，也不意味着要把全部事件送进当前提示。

## 案例：Pi 的极简选择

Pi 是一个极简代理脚手架。讲义列出的默认工具只有 `read`、`bash`、`edit`、`write`；代理以 ReAct 式循环作出工具调用。对话历史是树，可以回到旧分支继续；上下文通过事件到模型输入的转换、技能文件的逐步披露和压缩来管理。少量工具与简单内核让设计容易理解，社区扩展则可按需求增加功能。

这些选择也带来边界。讲义指出 Pi 默认没有子代理、计划模式和权限弹窗，进程拥有的权限就是代理执行时可用的权限。若要把类似脚手架放进自己的任务，应在运行环境和工具层明确授权范围，评估错误行动的代价。模式只有放到具体任务、权限和恢复方式中，才能判断是否合适。

## 复习与实践

- 画出一个任务的控制流，标出由代码决定和由模型决定的步骤。
- 说明何时用并行分区、并行投票或动态分派工作者；三者解决的问题不同。
- 为一个会产生长工具输出的代理，设计事件日志、压缩和观察遮蔽的组合，并列出不能丢失的约束。
- 检查「先规划再执行」的计划在工具失败或新证据出现时如何调整。
